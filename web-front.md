# Web Front Implementation Notes

最終更新: 2026-06-28

このファイルは、backend 実装を前提に Web UI を作るための短い指針。UI は `WEB_UI_DESIGN.md` を最優先し、ここでは API と状態境界だけを扱う。

## 基本方針

- 初期画面は Chat Shell。
- Workspace / Run History / Change History / Memory / Knowledge Wiki / Skill は、必要な時に drawer や detail view で見せる。
- Web UI は正本を持たない。正本は Workspace filesystem と SQLite index/history。
- UI は「状態を見る」「明示操作を投げる」「結果を再取得する」役割に徹する。
- provider secret や API key 入力欄は Settings UI に置かない。

## 起動確認

- `GET /api/health`
  - アプリ起動時の軽量確認に使う。
  - `lifecycle` は `started_at`, `uptime_ms`, `listening`, `closing`, `close_started_at`, `closed_at`, `scheduler_enabled`, `socket_clients` を返す。
  - `lifecycle.closing=true` または `closed_at` がある場合、frontend は送信操作を pending にせず再接続/再取得へ誘導する。
  - `workspace.ok` が false の場合でも、UI 全体は止めずに Context Drawer などで warning と repair plan への導線を出す。
  - `release.non_destructive.command` は外部副作用なしの release gate。非破壊gateには `gateway-recovery-probe` と `external-channel-probe` が含まれ、Gatewayの期限切れpairing/lock修復と外部channel readinessを secret値なしで確認する。`release.profiles[]` は `local_oss` と `production_ops` の運用profileを返す。`release.manual_gates[]` は実外部CLI run/resume、Docker/SSH/remote sandbox run、本物のSlack/Telegram/LINE/Email service credentialを使う外部チャネルE2Eの明示承認待ち項目。Frontend はこれを「完了」ではなく「manual opt-in required」と表示し、`confirmation_flag` と `runbook` を案内するだけにする。
  - `gateway.pairing_statuses`, `gateway.pairing_policy_statuses`, `gateway.pairing_policy_trust_modes`, `gateway.routing_policy_statuses`, `gateway.routing_policy_strategies`, `gateway.inbound_statuses`, `gateway.concurrency_lock_statuses` は Gateway の状態別summary。Frontend は一覧件数を独自集計せず、初期status badge / diagnostics にはこの summary を使う。
  - `gateway.slack_signature_configured`, `gateway.telegram_webhook_verification_configured`, `gateway.line_signature_configured`, `gateway.email_provider_webhook_verification_configured`, `gateway.email_provider_webhook_verification_providers[]` は inbound検証secretが設定済みかだけを返す。Frontend は secret値や署名計算を扱わず、未設定/設定済みの状態表示にだけ使う。
  - `gateway.active_concurrency_locks` は `concurrency_lock_statuses.acquired` の短縮値。cancel 後や expire 後は `/api/health` を再取得して詰まりが解けたか見る。
  - `gateway.sandbox_instance_statuses` / `gateway.sandbox_instance_backends` は sandbox lifecycle の診断summary。Docker/SSH/remote の実processやremote workspaceをFrontendから直接調べない。
- `GET /api/workspace/health`
  - Workspace の詳細診断に使う。
  - `layout`, `indexes.wiki`, `indexes.collections`, `issues`, `repair_plan` を表示できる。
- `POST /api/workspace/repair`
  - default は dry-run。実行する場合だけ `{ "dry_run": false }` を送る。
- `POST /api/gateway/repair`
  - default は dry-run。期限切れ pending pairing と期限切れ acquired concurrency lock の修復候補を `actions[]` で返す。
  - 実行する場合だけ `{ "dry_run": false }` を送る。Frontend は `actions[].target_ref`, `reason`, `before_status`, `after_status`, `status=planned/applied/skipped` を表示し、独自に pairing/lock を直接書き換えない。

## Chat Shell

- session 作成:
  - `POST /api/chat/sessions`
- session 一覧 / 詳細:
  - `GET /api/chat/sessions`
  - `GET /api/chat/sessions/:id`
- transcript:
  - `GET /api/chat/sessions/:id/transcript`
  - `session`, `messages`, `operations`, `policy_decisions`, `audit_records`, `artifacts`, `backend_runs`, `backend_events`, `tool_runs`, `workspace_changes`, `change_history`, `run_history` をまとめて返す。
  - UI はこの response を Run History / Change History / session export の正準 read API として扱う。
- resume state:
  - `GET /api/chat/sessions/:id/resume-state`
  - `can_resume=true` の時だけ `resumable_runs[]` を使って resume 操作を出す。
  - `resumable_runs[]` と `latest_run` は `id`, `backend_id`, `backend_kind`, `status`, `event_count`, `waiting_for_backend_input`, `waiting_event`, `last_event` を持つ。`waiting_event.payload` は backend-native prompt/状態の表示用で、UI が approval 可否を独自判断しない。
  - `next_required_action=submit_backend_native_input` の場合、対象 run に `POST /api/backend-runs/:runId/resume` を送る。
  - resume 成功時は run が `completed` または再度 `waiting_for_backend_input` になる。送信後は `resume-state` と `transcript` を再取得する。
  - `latest_run` は header や Run History の軽い状態表示に使える。
  - `transcript_counts` は badge / summary 用で、正本データとして扱わない。
- message 送信:
  - `POST /api/chat/sessions/:id/messages`
  - Web からの通常送信は backend 側で `source=web`, `actor_identity=owner`, `instruction_source=owner_instruction`, `session_key=web:owner:main` 系の `MessageEnvelope` になる。
  - frontend は `actor_identity` や `instruction_source` を自己判断で作らない。外部入力や scheduled/local bridge 入力は Gateway / backend が正規化する。
- backend locale contract:
  - `backend_events[]` の `event_type=run_started` は `payload.input_locale`, `payload.output_locale`, `payload.locale_contract` を持つ。
  - Native backend は `locale_contract.enforcement=provider_prompt`、External/Codex/Claude/Mock backend は `locale_contract.enforcement=prompt_and_environment`。
  - frontend は返答言語の独自判定をせず、Run History / debug表示ではこの contract と `MessageEnvelope.output_locale` を表示する。
- envelope preview:
  - `POST /api/gateway/envelope-preview`
  - Web/Cron/Local bridge/paired external の入力がどの `MessageEnvelope` へ正準化されるか確認する read-only preview。
  - request は `source` (`web`, `cron`, `local_cli`, `paired`), `user_intent`, `input_locale`, `output_locale`, `route`, `source_identity`, `source_label`, `account_id`, `thread_id`, `metadata` を受け取る。
  - response は `MessageEnvelope`。`actor_identity`, `source`, `session_key`, `input_locale`, `output_locale`, `metadata.instruction_source` を診断表示に使える。
- typed surface operation:
  - `POST /api/surface/operations`
  - `POST /api/surface/operations/dispatch-plan`
  - `GET /api/surface/renderers`
  - `GET /api/surface/contract`
  - `GET /api/domain/commands/diagnostics`
  - `message.submit`, `form.submit`, `table.patch`, `chart.request`, `artifact.request`, `collection.record.create`, `collection.record.patch`, `custom_view.action`
  - `dispatch-plan` は同じ request body を受け取り、実行せずに `{ dispatch_target, runtime_method, operation_name, result_kind, render_kind, requires_session, writes_workspace, output_resource_kind, proposed_effects }` を返す。
  - `dispatch_target` は `host_chat`, `collection_engine`, `artifact_pipeline`。frontend はこの値で勝手に処理を分岐せず、表示前診断・disabled reason・debug表示に使う。
  - `GET /api/surface/renderers` は標準 renderer と plugin/custom_view renderer の registry を返す。item は `id`, `kind`, `renderer`, `version`, `title`, `description`, `props_schema`, `actions_schema`, `fallback_kind`, `category`, `metadata` を持つ。
  - `GET /api/surface/contract` は `protocol_version`, `renderers`, `render_kinds`, `commands`, `input_sources` を返す。frontend はここで `DomainCommandEntry.output_render_kinds` と renderer registry を同時に読み、commandが返しうる固定surfaceを事前に判断できる。
  - `GET /api/domain/commands/diagnostics` は `ok`, `coverage`, `issues[]`, `recommendation` を返す。frontend は開発/診断表示でこの結果を使い、Domain Command / ActionCatalog / provider tool alias / surface operation alias / render kind の整合を自己実装しない。
  - 現在の `apps/web` は初期化時に `GET /api/surface/contract` を読み、Chat Shell の `message.submit` を `POST /api/surface/operations` 経由で送る。request には対応済み `renderer_capabilities` を含める。
  - Workspace Canvas は active Artifact から `form.submit`, `table.patch`, `chart.request`, `custom_view.action` を `POST /api/surface/operations` へ送れる。返却された `render_spec` は Workspace 内で固定surfaceとして表示する。
  - `custom_view` を受け取った場合、frontend は registry に `kind=custom_view` かつ `renderer` 一致の entry がある時だけ専用rendererへ渡し、無ければ `fallback` を使う。
  - request には任意で `renderer_capabilities` を付けられる。
    - `supported_kinds`: frontend が描画できる `SurfaceRenderSpec.kind` の配列。
    - `custom_view_renderers`: `custom_view` で対応できる renderer 名と version。
    - 未指定なら backend は全標準 renderer が使える前提で返す。
  - response の `result_kind` は `chat_turn`, `collection_record`, `collection_patch`, `artifact`, `form_submission`, `table_patch`, `chart_request`, `custom_view_action` のいずれか。
  - response には `render_spec` が含まれる。
  - `render_spec.kind` は `chat`, `collection_record` などの表示先を示す。
  - `render_spec.resource_refs` は UI が詳細再取得やリンク表示に使う参照。
  - `render_spec.props` は描画用の軽い補助情報。正本データとして保存しない。
  - `render_spec.negotiation` がある場合、backend が frontend capability に合わせて fallback を適用したことを示す。
    - `requested_kind`: backend が本来要求した表示種別。
    - `requested_renderer`: `custom_view` の本来 renderer。
    - `reason`: `unsupported_kind`, `unsupported_custom_renderer`, `invalid_fallback`。
    - `applied_fallback=false` の場合は `status_timeline` error として表示し、`errors[]` を出す。
- backend 選択:
  - `GET /api/agent-backends`
  - backend selector は chat header に置く。
  - `configured=false` は command/env 未設定。`connection_state=degraded` かつ `reason=command_not_found` は command は設定済みだが PATH/絶対path で解決できない状態。
  - `metadata.command_probe` がある場合、`resolved`, `path_kind`, `reason` を診断表示に使える。UI はこの情報をもとに command を推測・補完しない。
  - `metadata.stream_probe` がある場合、`enabled`, `status`, `reason`, `event_count`, `first_event_type`, `exit_code`, `stderr_summary` を診断表示に使える。
  - `stream_probe.status=not_configured` は probe未設定。`compatible` は短時間probeで正準JSON eventを読めた状態。`incompatible` / `failed` / `timeout` は実行候補として注意表示にするが、UI側で直接CLIを起動しない。
  - `supports.stream_events=true` は backend cassette が event replay/follow seam を持つことを示す。frontend は cassette を直接購読せず、下の socket event / events API を使う。
  - `kind=codex` の backend は既定で CLI JSONL 実行と native resume の contract を持つ。Frontend は CLI 引数や resume token を組み立てず、`supports.resume_run`, `supports.stream_events`, `metadata.command_probe`, `metadata.stream_probe` だけを見て操作可否と診断を出す。
  - `samurai-native` の ProviderAdapter / PromptBuilder / ContextBuilder / ToolLoop / ToolExecutor は backend 内部の分離。frontend はこれらを selector に出さず、`backend_id` と status だけを見る。
- backend event:
  - socket event `backend.event.created`
  - `GET /api/backend-runs/:runId/events`
  - `GET /api/backend-runs/:runId/tool-runs`
  - `GET /api/backend-runs/:runId/tool-runs/diagnostics`
  - `GET /api/tool-runs/diagnostics?session_id=<sessionId>&status=ignored`
  - `POST /api/backend-runs/:runId/cancel`
  - `POST /api/backend-runs/:runId/resume`
  - `POST /api/backend-runs/:runId/stream-sync`
  - socket event は UI 用 projection。長い tool output、secret らしき key、native input の中身は要約・伏せ字・`has_input` に変換される。
  - socket projection の `tool_call_started` は `tool_call_id`, `provider_tool_name`, `action_id`, `execution_boundary`, `requires_host_execution` などの安全な計画summaryだけを含む。`arguments` の完全版は persisted event 側で再取得する。
  - socket projection の `tool_call_output` は `action_id`, `status`, `reason`, `summary`, `gateway_boundary`, `secret_resolution` の安全なsummaryだけを含む。`stdout` / `stderr` / raw output / secret material は socket payload として扱わない。
  - backend が top-level `tool_call_id` を出した場合も、persisted/socket event では `payload.tool_call_id` として追跡できる。
  - 詳細な履歴や export は `GET /api/backend-runs/:runId/events` または session transcript の persisted event を再取得する。
  - ToolRun一覧は `GET /api/backend-runs/:runId/tool-runs` で再取得する。Context Drawer / Run History は `provider_tool_name`, `action_id`, `status`, `output_summary`, `resource_refs` を表示し、tool実行結果をfrontendで再構成しない。
  - 旧provider toolや未対応toolが繰り返し `ignored` / `failed` になる場合、`GET /api/backend-runs/:runId/tool-runs/diagnostics` または `GET /api/tool-runs/diagnostics` を使う。response は `groups[]`, `repeated_ignored_provider_tools[]`, `reasons[]`, `adapter_recommendations[]`, `recommendation` を返す。`adapter_recommendations[]` は `mapping_status`, `domain_command_id`, `suggested_next_step` を持つ。UI はこれを「adapter/catalog mappingの診断」として表示し、同じtoolを自動再試行しない。
  - UI は socket payload を正本として保存しない。表示中の timeline 更新だけに使う。
  - `stream-sync` は backend cassette の `streamEvents()` を Runtime 経由で同期し、response は `run`, `status`, `events[]`, `persisted_event_count`, `skipped_duplicate_count`, `timed_out`, `max_events_reached`。
  - `status` は `synced`, `unsupported`, `timeout`, `max_events`。`unsupported` の場合も `backend_stream_unavailable` event が保存される。
  - stream同期で保存される診断eventは `backend_stream_synced` / `backend_stream_unavailable`。UI は backend を直接購読せず、このAPIと persisted events を使う。
  - Gateway 経由の tool 判定は `tool_call_output.payload.gateway_boundary` に入る。
    - `decision`: `allowed` / `denied`
    - `reason`: `explicit_allow`, `wildcard`, `tool_not_allowed`, `no_policy`
    - `action_id`, `policy_id`, `allowed_tools`, `sandbox_mode`, `workspace_access`, `network_access`
  - Gateway boundary の判定と Runtime tool 実行は、初回 run と `resume` 後に出た `tool_call_started` の両方で同じ contract を使う。
  - `decision=denied` の場合、backend は `ToolRun(status=ignored)` と `WorkspaceChange(change_type=other)` を残す。UI は独自に再実行せず、Run History / Context Drawer で理由を見せる。
  - MCP / sandbox tool 実行の SecretRef 解決状態は、payload に `secret_resolution` がある場合だけ参照する。
    - `secret_ref_ids`: 対象 config が参照した SecretRef ID。
    - `resolved_secret_ref_ids`: 実行前に解決できた SecretRef ID。
    - `unresolved_secret_ref_ids`: 解決に失敗した SecretRef ID。
    - `unresolved_reasons`: SecretRef ID ごとの `missing`, `unsupported_source`, `file_root_required`, `file_outside_root`, `read_failed` など。
  - `secret_resolution` は UI / API 用の summary であり、secret の raw value や env/file key は含まれない。UI は値やkeyを推測・表示・保存しない。
  - tool が allowlist でブロックされた場合、SecretRef 解決は試行されない。`secret_ref_ids` があっても `unresolved_secret_ref_ids=[]` なら「未解決」ではなく「未実行」として扱う。
  - MCP tool が backend 側で実行された場合、backend は stdio JSON-RPC の `initialize` / `tools/call` を境界内で処理できる。frontend は MCP server process を直接起動・購読しない。
  - MCP / sandbox 実行で一時secret fileが必要な場合、backend は実行中だけ `0600` の一時fileを作り、実行後に削除する。UI/API に返るのは `secret_resolution` と通常の tool result だけ。
  - 外部 backend が event payload で `backend_session_id` / `conversation_id` / `thread_id` を返した場合、backend は `BackendRun.metadata.backend_session_id` に正規化して保存する。
  - UI は native session id を編集しない。Run History の診断表示や resume 可否説明にだけ使う。
  - JSONL code-agent backend の provider event は `payload.provider_event_type` に元event名、thread/session由来の resume token は `payload.backend_session_id`、必要なら `payload.provider_thread_id` に残る。
  - shell/command 実行系eventは `tool_call_started` / `tool_call_output` に正規化され、`payload.provider_tool_name=exec_command`, `payload.action_id=sandbox.exec`, `payload.exit_code`, `payload.stdout`, `payload.stderr`, `payload.status` を持つ。Runtime は `provider_tool_name` ではなく `action_id=sandbox.exec` を見て sandbox executor に接続する。UI は stdout/stderr を直接保存せず、詳細は persisted event を再取得する。
  - MCP系tool event は `payload.action_id=mcp.call`, `payload.server_name`, `payload.tool_name` を持つ場合がある。UI はこの情報を境界診断に使い、MCP process を直接起動しない。
  - `samurai-native` の tool request は `tool_call_started.payload.action_id`, `execution_boundary=host_runtime`, `requires_host_execution=true`, `arguments` を持つ。これは Host Runtime への実行計画であり、frontend が tool を実行・再実行する合図ではない。
  - `backend_waiting_for_native_input` は「外部 backend 側で入力待ち」という状態表示だけに使う。Web 側で別 approval UI に変換しない。
- cancel:
  - cancel は対象 run の状態を `cancelled` にする。
  - Gateway inbound 由来の run で `BackendRun.metadata.gateway_boundary_concurrency_lock_key` がある場合、backend は cancel 時に該当 lock を release する。UI は lock release API を直接叩かず、cancel 後の run metadata `gateway_concurrency_lock_status` / `gateway_concurrency_lock_released_at` と `GET /api/health.gateway.active_concurrency_locks` を再取得する。
  - すでに `completed` / `failed` / `cancelled` の run は、UI 側で追加操作を出さない。
- resume:
  - resume は `waiting_for_backend_input` の run だけに出す。
  - 非対応 backend では run event に `backend_resume_unsupported` が残る。
  - `supports.resume_run=true` の external CLI backend は、保存済み `BackendRun.metadata.backend_session_id` がある場合だけ native resume を試行する。
  - native session id がない場合は `backend_native_session_missing` が run event に残る。UI は native session id を手入力させず、Run History の診断として表示する。
  - resume 成功時は `GET /api/backend-runs/:runId/events` を再取得し、`backend_native_input_submitted` と続きの `text_delta` / `tool_call_started` / `tool_call_output` / `run_completed` / `run_failed` を見る。
  - resume 中に tool が実行・拒否された場合も、初回 run と同じ `ToolRunRecord`, `WorkspaceChange`, `payload.gateway_boundary` から結果を辿る。frontend が resume 用の別tool実行口を持つ必要はない。
- UI ルール:
  - 単純なチャット送信は `POST /api/chat/sessions/:id/messages` でよい。
  - form/table/chart/artifact/custom-view のように UI 由来の構造がある操作は `POST /api/surface/operations` を使う。
  - `surface_operation_id` と `surface_operation_kind` は BackendRun metadata に残る。
  - renderer は `operation.kind` ではなく、まず `render_spec.kind` と `result_kind` で分岐する。
  - frontend が描画できない `render_spec.kind` を自己判断で別表示に変換しない。必要なら次回以降の request に `renderer_capabilities` を送り、backend の negotiated fallback を受ける。
  - `custom_view` は `props.renderer` と `props.renderer_version` を見て対応可否を判断する。未対応なら `renderer_capabilities.custom_view_renderers` に含めない。

### `message.submit` SurfaceOperation vertical flow

- request:
  - `POST /api/surface/operations`
  - body: `{ id?, kind: "message.submit", session_id, content, input_locale?, output_locale?, backend_id?, renderer_capabilities?, metadata? }`
- response:
  - `result_kind: "chat_turn"`
  - `render_spec.kind: "chat"`
  - `result.backendRun.metadata.surface_operation_id`
  - `result.backendRun.metadata.surface_operation_kind: "message.submit"`
  - `result.backendEvents[]`: `run_started` / `text_delta` / `tool_call_started` / `tool_call_output` / `artifact_created` / `run_completed` など。
  - `result.workspaceChanges[]`: Artifact / Memory / Skill / Gateway boundary など、backend が保存した workspace feedback。
  - `result.artifacts[]`, `result.memories[]`, `result.toolRuns[]`, `result.reflectionRuns[]`, `result.reflectionSuggestions[]`
- UI ルール:
  - `message.submit` は Chat Shell 起点でも Surface Protocol 起点でも、Host の `runChatTurn` に合流する。
  - UI は Artifact / WorkspaceChange / Reflection を自前生成しない。返却された `result.*` と履歴APIを再取得して表示する。
  - 事前確認だけしたい場合は `POST /api/surface/operations/dispatch-plan` を使い、`dispatch_target=host_chat` / `result_kind=chat_turn` / `render_kind=chat` を見る。

## Context Preview / Freeze Snapshot

- context preview:
  - `GET /api/context/preview?session_id=<session_id>&q=<query>`
- response:
  - `context_assembly`
  - `session_summary`
  - `external_assist`
  - `active_memory[]`
  - `active_memory_report`
  - `knowledge_wiki[]`
  - `knowledge_wiki_report`
  - `collection_notes[]`
  - `skill_selection_report`
  - `selected_skills[]`
  - `session_search[]`
  - `available_tools[]`
  - `recent_messages[]`
  - `freeze_snapshot`
- `context_assembly`:
  - Host がこの turn 用に集めた文脈の診断用 contract。
  - `sources[]` は `session` / `recent_messages` / `freeze_snapshot` / `active_memory` / `knowledge_wiki` / `collection_notes` / `selected_skills` / `session_search` / `external_assist` / `available_tools` / `gateway_boundary` ごとの `status`, `candidate_count`, `included_count`, `reason` を返す。
  - `omissions[]` は古い message、上限外の search result、queryに合わなかった note、Gateway boundary で落ちた tool などの理由を返す。
  - `gateway_boundary` は preview では通常 `present=false`。Gateway inbound 由来の実行では BackendRun metadata と provider input 側で `present=true`, `policy_id`, `source_channel`, `available_tools_before_boundary`, `available_tools_after_boundary`, `filtered_tool_count` が入る。
  - `quality_checks[]` は `active_wiki_only`, `external_assist_isolated`, `collection_notes_context_only`, `freeze_snapshot_loaded` などの backend 自己検査結果。UI は警告表示に使ってよいが、frontend 側で context を再選別しない。
- `freeze_snapshot`:
  - `profile/SOUL.md` は backend が自動作成・読込する。
  - `profile/PROFILE.md` は存在する場合だけ読み込まれる。
  - `memory_refs`, `wiki_refs`, `skill_refs` は、その turn に注入された根拠の参照。
  - `stable_hash` は backend run metadata にも残る。
- context freeze:
  - `POST /api/context/freeze`
  - request は `session_id` 必須、任意で `query` または `q`。
  - response は `freeze_snapshot`, `context_assembly`, `session_summary`, `source_refs`, `stable_hash`, `created_at`。
  - UI は Debug / Context Drawer で、どの SOUL/Profile/Memory/Knowledge Wiki/Skill が固定文脈に入ったか確認するために使う。
  - UI 側で `SOUL.md` / `PROFILE.md` を生成・上書きしたり、`stable_hash` を再計算したりしない。
- Active Memory retrieval:
  - `active_memory[]` は通常注入対象だけ。`state` は `active | topic | sensitive` のみ。
  - `active_memory_report.excluded[]` は `session_only`, `provisional_pending`, `archived`, `not_active_state`, `empty_content` の除外理由を返す。
  - `active_memory_report.sensitive_redactions[]` は high sensitive の本文伏せや low sensitive の扱いを返す。
  - `active_memory_report.conflict_groups[]` と `resolution_suggestions[]` は、Memory View / Context Drawer 側で review 候補として表示できる。frontend が自動で merge/archive しない。
  - 専用確認API: `GET /api/memory/active-retrieval?q=<query>` は `{ active_memory, report }` を返す。
- Knowledge Wiki retrieval:
  - `knowledge_wiki[]` は通常注入対象だけ。`state=active` のページ本文だけが入る。
  - `knowledge_wiki_report.excluded[]` は `proposed`, `rejected`, `archived`, `not_active`, `empty_content` の除外理由を返す。
  - `knowledge_wiki_report.source_refs[]` は注入された active Wiki の根拠参照だけを返す。
  - 専用確認API: `GET /api/wiki/active-retrieval?q=<query>` は `{ knowledge_wiki, report, graph }` を返す。
  - 診断API: `GET /api/wiki/diagnostics` は active Wiki の本文有無、provenance検証状態、source_refs有無、active-only retrieval境界違反を `issues[]` と `recommendation` で返す。UI は Context Drawer / Knowledge Wiki detail で警告表示に使い、frontend側で正本やretrieval対象を再判定しない。
- BackendRun metadata:
  - `context_assembly_sources[]`: sourceごとの `kind`, `status`, `candidate_count`, `included_count`。
  - `context_assembly_gateway_boundary_present`: Gateway boundary が run に適用されたか。
  - `context_assembly_filtered_tool_count`: Gateway boundary で除外された available tool 数。
  - `context_assembly_quality_warnings[]`: backend 自己検査で `pass` 以外だった項目。
- External assist:
  - `external_assist.hints[]` は未検証ヒント。Memory / Knowledge Wiki / Skill の正本ではない。
  - 複数 provider が登録されている場合、`external_assist.hints[]` は providerごとの completed prefetch hint を結合した配列になる。UI は `provider_id` 単位の診断が必要な時だけ records / diagnostics API を見る。
  - `external_assist.last_prefetch` は直近の completed prefetch record。`phase=prefetch`, `status=completed|failed|skipped|disabled`, `provider_id`, `hints[]`, `error` を見る。
  - `external_assist.recent_failures[]` は外部補助の非致命的失敗。UI は警告表示に使えるが、Host context 自体は継続する。
  - run 完了後に external assist sync が動いた場合、互換用に `BackendRun.metadata.external_assist_sync_id`, `external_assist_sync_status`, `external_assist_sync_provider_id` が入る。複数 provider では `external_assist_sync_ids[]`, `external_assist_sync_statuses[]`, `external_assist_sync_provider_ids[]` を見る。
  - envで `SAMURAI_EXTERNAL_ASSIST_URL` を設定するとHTTP provider、`SAMURAI_EXTERNAL_ASSIST_FILE` を設定すると単体ローカルJSON/JSONL provider、`SAMURAI_EXTERNAL_ASSIST_FILES` を設定すると複数ローカルJSON/JSONL providerが `source_label` 付き未検証hintを返す。複数provider名は `SAMURAI_EXTERNAL_ASSIST_PROVIDER_IDS` で指定できる。API keyはSettingsに置かない。
  - `GET /api/health` は `external_assist.configured`, `provider_id`, `provider_ids[]`, `provider_count`, `source`, `provider_kind`, `token_configured`, `errors[]`, `warnings[]` を返す。endpointは `endpoint_origin` と path有無だけを返し、tokenやquery stringは返さない。
  - `GET /api/settings` / `PATCH /api/settings` は既存の保存方針に加えて read-only `external_assist_config` を返す。Settings UIはAPI key入力欄を作らず、補助の有効/無効とsafe diagnosticsだけを表示する。
- External assist diagnostics API:
  - `GET /api/external-assist?session_id=<session_id>&phase=prefetch|sync&limit=20`
  - response は `ExternalAssistRecord[]`。
  - `GET /api/external-assist/diagnostics?session_id=<session_id>&phase=prefetch|sync&status=completed|failed|skipped|disabled&provider_id=<provider>&limit=100`
  - diagnostics response は `total_records`, `failed_records`, `hint_count`, `groups[]`, `violations[]`, `recent_failures[]`, `recommendation` を返す。
  - `violations[]` は `external_assist_not_isolated` / `external_assist_included_in_active_memory` を返す。ここに値が出た場合、frontend はそのhintをMemoryとして扱わず警告表示だけに留める。
  - `included_in_active_memory` は false のまま扱う。frontend が accepted Memory として表示・保存する場合は、別の proposal/accept flow を通す。
- frontend が勝手に判断してはいけないこと:
  - `available_tools[]` を UI 側で復活させない。
  - `external_assist` を accepted Memory として表示・保存しない。
  - `collection_notes[]` を Collection schema field として扱わない。
  - `knowledge_wiki[]` 以外の proposed/rejected/archived Wiki を回答根拠として混ぜない。
- UI ルール:
  - `freeze_snapshot.content` は通常の Chat Shell にそのまま大きく出さない。
  - Debug / Context Drawer では `SOUL.md`, `PROFILE.md`, refs, hash を確認できる。
  - UI 側で `SOUL.md` を勝手に生成・上書きしない。

## Localization Backend

- Resource detail translation:
  - `GET /api/artifacts/:id?target_locale=en`
  - `GET /api/memory/:id?target_locale=en`
  - `GET /api/skills/:id?target_locale=en&source_locale=ja`
  - `GET /api/wiki/:id?target_locale=en`
  - `GET /api/collections/:collectionId/records/:recordId?target_locale=en`
  - response は既存 detail payload に `locale` と、`target_locale` 指定時だけ `translation_resolution` を追加する。
  - `locale` は `source_ref`, `source_locale`, `content_locale`, `target_locale`, `fallback_locale`, `original_hash`。
  - `translation_resolution` は `source=translation|fallback`, `status=verified|draft|missing`, `text`, `target_locale`, 任意で `translation`。
- Resource translation records:
  - `GET /api/resource-translations`
  - query は任意で `source_kind`, `source_id`, `source_uri`, `source_label`, `target_locale`, `status`。
  - `POST /api/resource-translations`
  - request は `source_ref`, `source_locale`, `target_locale`, `original_hash`, 任意で `id`, `status`, `translated_text`, `provenance`。
  - `POST /api/resource-translations/resolve`
  - request は `source_ref`, `target_locale`, 任意で `original_hash`, `fallback_text`。
- Automatic translation jobs:
  - `POST /api/resource-translations/jobs`
  - request は `source_ref`, `target_locale`。任意で `source_locale`, `schedule`, `title`, `enabled`, `next_run_at`, `max_attempts`。
  - response は通常の Runtime write payload。`resource.kind=resource_translation`, `resource.delivery_target.source_ref`, `source_locale`, `target_locale`, `original_hash` を持つ。
  - job 実行は `POST /api/automation/jobs/run-due` または scheduler tick で行う。
  - 実行結果は `resource_translations` に `status=draft` として保存される。UIで公開済み扱いにする時は、別途 verified 保存/更新を使う。
- UI ルール:
  - 原文 resource は書き換えない。翻訳は必ず派生データとして扱う。
  - `locale.original_hash` と translation の `original_hash` がズレたら stale と見なし、detail API は fallback を返す。
  - `source=translation` かつ `status=verified` だけを「確認済み翻訳」として強く表示する。`draft` は候補表示に留める。
  - frontend 側で resource 本文を hash 計算しない。backend の `locale.original_hash` を使う。

- UI ルール:

  - `proposed`, `rejected`, `archived` は履歴・レビュー用。
  - `errors` がある reindex 結果は、成功扱いにせず warning として表示する。

- runtime selection:
  - Context Preview の `skill_selection_report` は Skill index 検索候補、選択済みSkill、除外理由を返す。
  - `selected_skills[].selection` は `score`, `matched_terms`, `matched_capabilities`, `missing_capabilities`, `unsupported_scopes`, `reasons[]` を持つ。

  - `skill_selection_report.excluded[]` は `missing_capability`, `scope_unsupported`, `low_match` の理由を返す。
- diagnostics:
  - `GET /api/skills/diagnostics`
  - response は selectable Skill（`project | active | pinned`）の本文有無、provenance検証状態、source_refs有無、support file有無/空ファイル、usage有無、allowed scope不整合を `issues[]` と `recommendation` で返す。
- project 保存:
  - `POST /api/skills/projects`
- 詳細:
  - `GET /api/skills/:id`
- support files:
  - `GET /api/skills/:id/support`
  - `POST /api/skills/:id/support`
- UI ルール:
  - support files は `references/`, `templates/`, `assets/`, `scripts/` などの補助資料として見せる。
  - Skill 本文と support files は混ぜて編集しない。
  - Curator run は dry-run proposal として扱う。frontend が `curatorReport.skill_actions[]` を見て、ユーザー操作後に apply API を呼ぶ。
  - `curatorReviewReport` は表示・レビュー用。frontend が勝手に merge / consolidate / patch を適用しない。
  - `protected_skills[]` に入った Skill には archive/stale ボタンを出さない。
  - `GET /api/reflection/diagnostics` は Reflection / Curator の運用警告として表示し、frontend 側で self-improvement 状態を再計算しない。
  - `GET /api/skills/diagnostics` は Context Drawer / Skill detail の警告表示に使う。frontend 側で Skill selection を再計算しない。
  - Evaluation run は実行ログレビューとして扱う。frontend は `evaluationReport` を Run History / Context Drawer に表示し、`suggestions[]` の apply API を通さずに Memory/Skill/Wikiを書き換えない。
  - reflection の `skill` suggestion は候補であり、`apply` か `POST /api/skills/candidates` を通るまで正本Skill扱いしない。
  - user correction 由来の candidate は、本文中の `User correction signals` を人間が確認してから project/active に進める。

## Action Catalog / Plugin Manifest

- ActionCatalog:
  - backend は built-in actions と plugin manifest を `packages/action-catalog` で管理する。
  - entries には `display_name`, `implementation_target`, `ui_display_category` がある。
- API:
  - `GET /api/action-catalog`
  - query は任意で `category`。
  - response は `actions`, `plugins`, `issues`。
  - `GET /api/plugins`
  - response は `plugins`, `entrypoints`, `issues`。
  - `GET /api/plugins/diagnostics`
  - diagnostics は filesystem plugin の manifest load issue、entrypoint readiness、signature status、missing handler、marketplace plugin count を返す。frontend は runtime handler可否を再計算しない。
- Plugin runtime loader:
  - filesystem plugin は workspace の `.codex-plugin/plugin.json` または `plugins/*/plugin.json` / `plugins/*/.codex-plugin/plugin.json` から discovery される。
  - manifest の `entrypoint` は plugin directory 内の相対パスだけが有効。
  - `plugins[].entrypoint_status` は `not_declared`, `ready`, `missing`, `outside_plugin`, `integrity_mismatch`。
  - `plugins[].signature_status` は `not_declared`, `trusted`, `untrusted_key`, `invalid`。
  - `plugins[].registered_handler_ids` / `missing_handler_ids` で実行可能性を見る。
  - `metadata.entrypoint_sha256` がある場合、backend は entrypoint の sha256 と照合する。
  - `metadata.plugin_signature` が trusted key で検証された entrypoint だけがデフォルトで自動ロードされる。未署名 entrypoint の実行は backend process config の明示許可が必要。
- UI ルール:
  - action discovery と policy decision を混ぜない。
  - `risk`, `approval`, `policy` は ActionCatalog に足さない。
  - 操作の許可・監査・rollback は runtime / policy / audit の結果を見る。
  - frontend は `missing_handler_ids` が残る plugin action を実行可能に見せない。

- Audit / rollback:
  - `GET /api/audit`

- UI ルール:

## External Send

- API:
  - `GET /api/external-sends`
  - `POST /api/external-sends`
  - `POST /api/external-sends/:id/dispatch`
  - `GET /api/external-sends/diagnostics`
- diagnostics:
  - query は任意で `stale_after_hours`。
  - response は `dispatch_enabled`, `dry_run_default`, `status_counts`, `channel_counts`, `transport_status_counts`, `transport_readiness[]`, `issues[]`, `recommendation` を返す。
  - `transport_readiness[]` は channelごとの `status`, `configured`, `dispatch_enabled`, `requires_target_url`, `message` を返す。UI は webhook/slack/telegram/line/email の送信可否を自前推測せず、この値を使う。
  - `issues[].code` は `external_send_pending_approval`, `external_send_dry_run_only`, `external_send_failed`, `external_send_stale_draft`, `external_send_missing_target_url`。
  - diagnostics は target の raw URL / token / secret を返さない。UI は `resource_ref` と `send_id` から詳細APIへ遷移する。

- UI ルール:
  - 本番送信は backend の `external.send.dispatch` と approval/policy flow を通す。
  - `dry_run_default=true` のとき、UI は「送信済み」と表示しない。
  - target URL や provider secret を frontend 側で補完・保存しない。
  - `external_send_missing_target_url` は Settings のsecret入力ではなく、backend target config の診断として表示する。Slack API は `channel_id`、Telegram は `chat_id`、LINE は `reply_token` または `to` 系target、Email SMTP は `to` / `cc` / `bcc` が必要。
  - failed / stale / pending は Run History / Context Drawer の警告として扱い、自動再送しない。

## Gateway

- pairing:
  - `GET /api/gateway/pairings`
  - query は任意で `status`, `channel`, `source_identity`, `session_key`, `limit`。外部sourceごとの絞り込みはこのAPIに任せ、frontend側で session key を自作しない。
  - `POST /api/gateway/pairings/:id/approve`
  - `POST /api/gateway/pairings/:id/reject`
  - `POST /api/gateway/repair` は期限切れ pairing と期限切れ acquired concurrency lock の dry-run/apply に使う。pairing 個別の approve/reject/rotate/revoke と混ぜず、診断・修復導線として扱う。
- diagnostics:
  - `GET /api/gateway/diagnostics`
  - response は pending pairing、blocked/failed inbound、active/expired concurrency lock、failed sandbox instance / workspace sync、pairing policy と routing policy の片側欠落を `issues[]` と `recommendation` で返す。
  - UI は Gateway detail / Context Drawer / Settings の警告表示に使い、frontend 側で pairing/routing/session key/lock を直接修復しない。
- pairing policy:
  - `GET /api/gateway/pairing-policies`
  - `GET /api/gateway/pairing-policies/:channel`
  - `POST /api/gateway/pairing-policies`
  - `channel` は `telegram`, `slack`, `line`, `email`, `webhook`, `local_cli`, `cron`。
  - `status` は `enabled` / `disabled`。`disabled` は inbound を `gateway_pairing_policy_disabled` で止める。
  - `trust_mode` は `pairing_required`, `auto_approve`, `blocked`。`auto_approve` は backend が approved pairing を作ってから route する。Frontend は独自に auto approve しない。
  - `allowlist` は `*`, `source_identity`, `channel:*`, `channel:source_identity` を扱う。マッチしない inbound は `gateway_source_not_allowed` で blocked になる。
  - `pairing_ttl_ms`, `duplicate_window_ms`, `rate_limit_window_ms`, `rate_limit_max` は backend guard の値。UI はこれを表示・保存できるが、client-side rate limit の正本にしない。
  - inbound / pairing の `metadata.gateway_pairing_policy` と `metadata.gateway_source_scope` から、どの policy と source scope で処理されたか確認できる。
  - 保存済み policy が無い channel でも、GET は backend default を返す。`telegram` / `slack` / `line` / `email` / `webhook` は `pairing_required`、`local_cli` / `cron` は `auto_approve` が既定。
- routing policy:
  - `GET /api/gateway/routing-policies`
  - `GET /api/gateway/routing-policies/:channel`
  - `POST /api/gateway/routing-policies`
  - `POST /api/gateway/session-routing/preview`
  - `channel` は `telegram`, `slack`, `line`, `email`, `webhook`, `local_cli`, `cron`。
  - `session_key_strategy` は `account_thread`, `account_main`, `channel_main`。
  - routing preview request は `channel`, `source_identity`, 任意で `source_label`, `account_id`, `thread_id`, `route`, `metadata`。response は `{ input, policy, resolution }` で、`resolution.session_key`, `account_id`, `thread_id`, `route`, `allowed`, `reason`, `session_key_strategy` を返す。
  - `account_thread` は `channel:account_or_source:thread_or_route` で、既定の隔離単位。
  - `account_main` は同じ account/source を `default_route` にまとめる。
  - `channel_main` は channel 全体を `default_route` にまとめるため、UI は通常の外部channelで安易に選ばない。
  - `default_account_id`, `default_thread_id`, `default_route` は backend が session key を作るための補助値。Frontend は session key を自作せず、inbound / pairing の `session_key` と `metadata.gateway_routing_policy` / `metadata.gateway_source_scope` を読む。
  - `status=disabled` の routing policy は inbound を `gateway_routing_policy_disabled` で止める。
- inbound:
  - `GET /api/gateway/inbound`
  - `POST /api/gateway/inbound`
  - POST body は `channel`, `source_identity`, `body` が必須。任意で `source_label`, `account_id`, `thread_id`, `route`, `input_locale`, `output_locale`, `backend_id`, `metadata` を渡せる。
  - `POST /api/gateway/webhooks/:source_identity`
  - webhook endpoint は JSON payload の `body` / `text` / `message` / `content` / `user_intent` / `prompt`、または `event.*` / `payload.*` / `data.*` から本文を抽出し、`channel=webhook` の inbound として同じ Gateway path に流す。任意で `source_label`, `account_id`, `thread_id`, `route`, `input_locale`, `output_locale`, `backend_id`, `metadata` を body または query で渡せる。
  - webhook response は `{ ...GatewayInboundRuntimeResult, adapter: { channel: "webhook", source_identity, body_field } }`。`adapter.body_field` はどの payload field を本文として採用したかの診断用で、UI が本文を再抽出するためには使わない。
  - webhook metadata は `metadata.gateway_webhook_adapter=true`, `gateway_webhook_body_field`, `gateway_webhook_payload_keys[]` を持つ。`metadata` 内の secret-like key/value は redaction 済み。Frontend は raw webhook payload を保存・表示しない。
  - `POST /api/gateway/slack/events`
  - Slack event endpoint は `type=url_verification` の `challenge` を返し、message event の `event.text` または top-level text/body系fieldを `channel=slack` の inbound として同じ Gateway path に流す。
  - Slack event response は `{ ...GatewayInboundRuntimeResult, adapter: { channel: "slack", source_identity, body_field, team_id?, channel_id?, user_id? } }`。backend は `team:<team>/user:<user>` を source identity、`team:<team>` を account、`channel:<channel>/thread:<thread_ts|ts>` を thread として routing policy に渡す。
  - Slack署名検証は `SAMURAI_SLACK_SIGNING_SECRET` が設定されている時だけ必須。設定済みの場合、backend は `X-Slack-Signature` / `X-Slack-Request-Timestamp` を検証し、失敗時は `401 { error: "invalid_gateway_slack_signature", signature_status, reason }` を返して inbound を保存しない。
  - Slack metadata は `metadata.gateway_slack_adapter=true`, `gateway_slack_signature_status`, `gateway_slack_body_field`, `gateway_slack_payload_keys[]`, event/team/channel/user/thread summaryを持つ。top-level `token` などの secret-like payload key/value は保存しない。実Slack API呼び出しはこのbackend sliceではまだ扱わない。
  - `POST /api/gateway/telegram/updates`
  - Telegram update endpoint は Telegram webhook update の `message.text` / `message.caption` などを `channel=telegram` の inbound として同じ Gateway path に流す。任意で `source_identity`, `source_label`, `account_id`, `thread_id`, `route`, `input_locale`, `output_locale`, `backend_id`, `metadata` を body または query で渡せる。
  - Telegram update response は `{ ...GatewayInboundRuntimeResult, adapter: { channel: "telegram", source_identity, body_field, update_id?, chat_id?, user_id?, message_id? } }`。backend は既定で `user:<from.id>` または `chat:<chat.id>` を source identity、`chat:<chat.id>` を account、`thread:<message_thread_id>` または `main` を thread として routing policy に渡す。
  - Telegram webhook verification は `SAMURAI_TELEGRAM_WEBHOOK_SECRET` が設定されている時だけ必須。設定済みの場合、backend は `X-Telegram-Bot-Api-Secret-Token` を検証し、失敗時は `401 { error: "invalid_gateway_telegram_secret", verification_status, reason }` を返して inbound を保存しない。
  - Telegram metadata は `metadata.gateway_telegram_adapter=true`, `gateway_telegram_verification_status`, `gateway_telegram_body_field`, `gateway_telegram_payload_keys[]`, update/chat/user/message summaryを持つ。top-level `token` などの secret-like payload key/value は保存しない。実Telegram API呼び出しはこのbackend sliceではまだ扱わない。
  - `POST /api/gateway/line/events`
  - LINE event endpoint は LINE webhook events の最初のroutable message textを `channel=line` の inbound として同じ Gateway path に流す。任意で `source_identity`, `source_label`, `account_id`, `thread_id`, `route`, `input_locale`, `output_locale`, `backend_id`, `metadata` を body または query で渡せる。
  - LINE event response は `{ ...GatewayInboundRuntimeResult, adapter: { channel: "line", source_identity, body_field, event_index, source_type?, user_id?, group_id?, room_id?, message_id? } }`。backend は既定で `user:<userId>` / `group:<groupId>` / `room:<roomId>` を source identity、group/room/user を account、`main` を thread として routing policy に渡す。
  - LINE署名検証は `SAMURAI_LINE_CHANNEL_SECRET` が設定されている時だけ必須。設定済みの場合、backend は raw body と `X-Line-Signature` を検証し、失敗時は `401 { error: "invalid_gateway_line_signature", signature_status, reason }` を返して inbound を保存しない。
  - LINE metadata は `metadata.gateway_line_adapter=true`, `gateway_line_signature_status`, `gateway_line_body_field`, `gateway_line_payload_keys[]`, event/source/message summaryを持つ。top-level `token` や `replyToken` などの secret-like payload key/value は保存しない。実LINE API呼び出しはこのbackend sliceではまだ扱わない。
  - `POST /api/gateway/email/messages`
  - Email message endpoint は email風JSON payload の `body` / `text` / `plain_text` / `text_body` / `message` / `content` / `html` / `html_body`、または本文なしの `subject` を `channel=email` の inbound として同じ Gateway path に流す。任意で `source_identity`, `source_label`, `account_id`, `thread_id`, `route`, `input_locale`, `output_locale`, `backend_id`, `metadata` を body または query で渡せる。
  - Email message response は `{ ...GatewayInboundRuntimeResult, adapter: { channel: "email", source_identity, body_field, from?, to?, subject?, message_id? } }`。backend は既定で `email:<from>` を source identity、`mailbox:<to>` を account、`message:<message_id>` / `reply:<in_reply_to>` / `subject:<stableHash(subject)>` を thread として routing policy に渡す。
  - `POST /api/gateway/email/imap/poll`
  - Email IMAP poll endpoint は backend env の `SAMURAI_EMAIL_IMAP_HOST` / `SAMURAI_EMAIL_IMAP_USER` / `SAMURAI_EMAIL_IMAP_PASSWORD` を使い、IMAP `UNSEEN` message を取得して同じ Email Gateway path に流す。response は `{ transport: { channel: "email", transport: "imap", mailbox, mark_seen, scanned, message_count, skipped_count }, messages[], skipped[] }`。`messages[]` の各要素は `uid`, `adapter`, `inbound`, 必要に応じて `pairing` / `session` / `chat` を持つ。
  - IMAP poll は既定で既読化しない。`mark_seen=true` または `SAMURAI_EMAIL_IMAP_MARK_SEEN=true` の時だけ `\Seen` を付ける。Frontend は IMAP host/user/password を保存・補完せず、poll結果と Gateway pairing/routing state だけを表示する。
  - `POST /api/gateway/email/provider-webhooks/:provider`
  - Email provider webhook endpoint は `provider=postmark | mailgun | sendgrid` を受け、各provider styleのpayloadを同じ Email Gateway path に正規化する。response は `{ ...GatewayInboundRuntimeResult, adapter: { channel: "email", provider, source_identity, body_field, from?, to?, subject?, message_id? } }`。
  - Email provider webhook verification は設定時だけ必須。Postmark は Basic Auth、Mailgun は webhook signature、SendGrid は signed webhook headers を検証し、失敗時は `401 { error: "invalid_gateway_email_provider_webhook_verification", provider, verification_status, reason }` を返して inbound を保存しない。Frontend は `verification_status` を表示するだけで、署名計算やsecret保存はしない。
  - Email metadata は `metadata.gateway_email_adapter=true`, `gateway_email_body_field`, `gateway_email_payload_keys[]`, from/to/subject/message summaryを持つ。IMAP経由では `gateway_email_imap_transport`, `gateway_email_imap_uid`, `gateway_email_imap_mailbox`、provider webhook経由では `gateway_email_provider_webhook`, `gateway_email_provider`, `gateway_email_provider_verification_status`, `gateway_email_provider_payload_keys[]` も残る。top-level `token` などの secret-like payload key/value と `metadata` 内の secret-like key/value は保存しない。実service credential込みの長時間E2Eは `production_ops` profile の manual gate として表示する。SMTP送信はExternal SendのEmail transportで扱う。
  - blocked response は `{ inbound, pairing? }` を返す。`inbound.status=blocked`, `inbound.error`, `pairing.status=pending` を見て、Chat Shell へは流さない。
  - processed response は `{ inbound, pairing, boundaryPolicy, concurrencyLock, session, chat }` を返す。
    - `session.session_key` が Gateway routing 後の正本。
    - `boundaryPolicy` は inbound 専用の execution boundary。UI はここから allowed tools / sandbox を表示できるが、再計算しない。
    - `chat.backendRun.metadata.gateway_inbound_id`, `gateway_channel`, `gateway_source_identity`, `gateway_pairing_policy_id`, `gateway_routing_policy_id`, `gateway_boundary_policy_id` を run history の紐づけに使う。
    - `chat.backendEvents[]`, `chat.toolRuns[]`, `chat.workspaceChanges[]`, `chat.reflectionRuns[]`, `chat.reflectionSuggestions[]` は通常 chat turn と同じ読み方でよい。
  - failed response / failed inbound record の `error` は backend 側で secret-like string redaction 済み。UI は復元しない。
  - concurrency lock は backend が inbound 処理の finally で release する。UI は `concurrencyLock.status` と `/api/health.gateway.active_concurrency_locks` を再取得して表示する。
- MCP config:
  - `GET /api/gateway/mcp-configs`
  - `GET /api/gateway/mcp-configs/:id`
  - `POST /api/gateway/mcp-configs`
  - GET response は sanitized summary。`secret_ref_ids`, `transport`, `enabled`, `allowed_tools`, `has_stdio`, `has_http`, `timeout_ms` は見えるが、SecretRef の `key` や raw secret value は返らない。
  - POST は backend config 管理用。stdio command / args / env binding / secret file binding を保存できるが、通常の Chat Shell UI から編集導線を先に作らない。
  - `transport=stdio` と `transport=http` は backend 実行差分で、frontend の event handling は同じ。HTTP の secret header binding も frontend には `secret_ref_ids` と `secret_resolution` としてだけ見える。
  - stdio MCP server process は backend 側で pool され、API server shutdown 時に backend が閉じる。frontend は MCP process の起動、購読、再利用、終了を直接扱わない。
  - `GET /api/health` の `gateway.mcp_process_pool` は backend 内の stdio MCP process pool 診断。`process_count`, `max_processes`, `idle_ttl_ms`, `servers[] { server_name, last_used_at }` を表示補助に使えるが、process 制御UIは作らない。
  - backend tool event `mcp.call` が実行された場合、Run History / event stream の `tool_call_output.payload` は `status`, `action_id=mcp.call`, `server_name`, `tool_name`, `reason`, `error`, `output`, `secret_resolution`, `sandbox`, `gateway_boundary` を返す。
  - `mcp.call` の `output` は backend 側で SecretRef material が redacted 済み。frontend は `secret_resolution.secret_ref_ids`, `resolved_secret_ref_ids`, `unresolved_secret_ref_ids`, `unresolved_reasons` だけを診断に使い、SecretRef `key` や raw secret value を表示しない。
  - `ToolRunRecord` は `provider_tool_name=mcp.call`, `action_id=<server_name>/<tool_name>` を持ち、`resource_refs` に `gateway_mcp_config` と `gateway_boundary_policy` が入る。
  - Sandbox execution:
    - lifecycle:
      - `GET /api/gateway/sandbox-instances`
      - `GET /api/gateway/sandbox-workspace-syncs`
      - `POST /api/gateway/sandbox-instances/:id/recreate`
      - `POST /api/gateway/sandbox-instances/:id/delete`
      - `POST /api/gateway/sandbox-instances/:id/sync`
      - `GatewaySandboxInstanceRecord` は `instance_key`, `scope`, `backend`, `status`, `sandbox`, `session_key`, `workspace_root`, `last_used_at`, `deleted_at` を返す。secret value、SSH key path、実container id は返さない。
      - `status=ready/recreated/deleted/failed` は backend lifecycle record の状態。Frontend は Docker / SSH / remote daemon を直接操作せず、recreate/delete API の結果と `/api/health` を再取得する。daemon実行結果は `metadata.lifecycle_status`, `metadata.lifecycle_reason`, `metadata.lifecycle_error`, `metadata.lifecycle_resource_refs` を見る。
      - `POST /api/gateway/sandbox-instances/:id/sync` の request は `{ direction?: "seed_to_sandbox" | "pull_from_sandbox" | "mirror", dry_run?: boolean }`。`dry_run` 既定は `true` なので、UI は preview を表示してから明示操作で `dry_run=false` を送る。
      - sync response は `{ dry_run, sync }`。`sync.status` は `planned/completed/failed/skipped`、`sync.direction`, `workspace_root`, `remote_workspace_root`, `error`, `started_at`, `completed_at`, `metadata` を返す。
      - `dry_run=false` は backend の sync adapter を実行し、結果を `GET /api/gateway/sandbox-workspace-syncs` に履歴として残す。Docker bind mount は `status=completed` / `metadata.sync_reason=docker_bind_mount`、Docker container は `docker cp`、SSH / remote は `rsync` または `metadata.workspace_sync_transport=local` の local copy を使う。
      - `direction=mirror` は backend が二方向syncとして扱う。local transport は newer-wins、Docker/SSH/remote は two-pass update として `metadata.sync_reason` に残る。Frontend は conflict resolution を独自判断しない。
      - SSH / remote で `ssh_target` / `remote_target` が無い場合は `status=failed` と `error` を返す。Frontend は失敗理由を表示するだけで、remote daemon や secret path を直接推測しない。
      - `/api/health.gateway.sandbox_executor_statuses[]` は `{ backend, available, command, reason, detail }` を返す。`none` は host process、`docker` は `docker --version`、`ssh` / `remote` は `ssh -V` の軽量probe。Frontend はこの診断を表示に使うだけで、Docker/SSHを直接起動しない。
      - `/api/health.gateway.sandbox_workspace_sync_statuses` は sync 履歴の状態summary。Frontend は `skipped/failed` を「同期完了」と表示しない。
  - backend tool event `sandbox.exec` が実行された場合、Run History / event stream の `tool_call_output.payload` は `status`, `action_id=sandbox.exec`, `command`, `exit_code`, `signal`, `stdout`, `stderr`, `reason`, `error`, `secret_resolution`, `sandbox`, `gateway_boundary` を返す。
  - sandbox lifecycle instance がある場合、`tool_call_output.payload.sandbox_instance` と `ToolRunRecord.resource_refs[kind=gateway_sandbox_instance]` から関連する instance を辿れる。
  - `stdout` / `stderr` / `error` は backend 側で SecretRef material が redacted 済み。frontend は SecretRef ID と resolution summary だけを診断表示に使う。
  - `ToolRunRecord` は `provider_tool_name=sandbox.exec`, `action_id=sandbox.exec` を持ち、`resource_refs` に `gateway_sandbox_execution` と `gateway_boundary_policy` が入る。
  - Docker / SSH / remote sandbox の実行詳細、secret file path、env value は frontend に表示しない。実行可否や失敗理由は `sandbox`, `reason`, `error` だけを見る。
  - SSH / remote sandbox の SecretRef file binding は backend が remote shell 内の一時dirに materialize し、実行後に cleanup する。frontend/API は remote path を正本として保存せず、`secret_resolution` summary だけを見る。
- UI ルール:
  - unknown external input は Chat Shell に直接混ぜない。
  - `blocked` / `pending` は Context Drawer に出す。
  - paired / trusted になった入力だけが session に流れる。
  - SecretRef は backend/runtime の config 参照であり、frontend は secret value を入力・保存・送信しない。
  - MCP / sandbox 実行で `secret_resolution.reason=secret_resolution_failed` 相当の失敗が返った場合、UI は SecretRef ID と reason だけを診断表示に使う。
  - secret の復旧導線を出す場合も、Settings に provider secret 入力欄を作らず、env/process/file config の確認として扱う。
  - MCP / sandbox の process config、env binding、secret file binding は backend config 管理の領域。frontend は config editor を先に作らず、Run History / Context Drawer で summary を表示するだけに留める。

## Secret Redaction Contract

- backend は Runtime / Gateway metadata、provider error response、internal server log / 500 response で secret-like key/value を redaction する。
- 対象:
  - key: `secret`, `token`, `api_key`, `api-key`, `password`, `credential`, `authorization`, `cookie` を含む field。
  - value: `Bearer ...`, `key=...`, `api_key=...`, `authorization: ...`, `token=...`, `password=...` などの文字列。
- Provider 失敗時の API response は `error`, `reason`, `provider`, `model`, `status`, `retryable` と、redacted 済みの run payload だけを返す。raw provider body / Authorization header / API key / password は返らない。
- Frontend は redaction 前提の値をさらに復元・推測しない。`[redacted]` または `[redacted:<secret_ref_id>]` は表示用診断としてだけ扱う。

## Backend Completion Handoff

- 接続の起点:
  - Chat: `POST /api/chat/sessions`, `POST /api/chat/sessions/:id/messages`, `GET /api/chat/sessions/:id/transcript`
  - Surface: `POST /api/surface/operations`, `POST /api/surface/operations/dispatch-plan`, `GET /api/surface/renderers`, `GET /api/surface/contract`
  - Context: `GET /api/context/preview`, `POST /api/context/freeze`
  - Workspace health/recovery: `GET /api/workspace/health`, `POST /api/workspace/repair`, backup/restore APIs
  - File / Browser action diagnostics: `GET /api/tools/file-browser/diagnostics`
  - External send: `GET /api/external-sends`, `GET /api/external-sends/diagnostics`, `POST /api/external-sends/:id/dispatch`
  - Gateway: pairing/routing/inbound/MCP/sandbox APIs under `/api/gateway/*`
  - Automation: scheduler/queue/job APIs under `/api/automation/*`
- 状態の正本:
  - filesystem: Artifact / Memory / Knowledge Wiki / Skill 本文
  - SQLite: index / history / status / audit / queue / Gateway control-plane
  - frontend: 表示状態だけ。正本を書き換えない。
- render:
  - 初期化時に `GET /api/surface/contract` を読み、対応rendererとDomain Commandの `output_render_kinds` を同期する。
  - Chat Shell / Artifact card / Workspace canvas は、contract由来の renderer title を小さい surface chip として表示する。
  - `form`, `table`, `chart`, `custom_view(renderer=generic)` は frontend capability として宣言し、backend に fallback 判断を任せる。
  - すべての SurfaceOperation response は `result_kind` と `render_spec` を見る。
  - `renderer_capabilities` を送れば backend が fallback を決める。frontend は fallback を独自変換しない。
- error / retry / resume:
  - provider failure は provider error payload の `reason`, `status`, `retryable` を見る。
  - `waiting_for_backend_input` は `resume-state` と `POST /api/backend-runs/:runId/resume` で扱う。
  - queue retry は `/api/automation/jobs/:id/requeue` / `release-lock` を使う。
  - Gateway lock は cancel / repair / health 再取得で扱い、frontend が lock record を直接書き換えない。
- 実装制限:
  - Frontend UI は Chat Shell / Workspace Canvas / basic fixed surface renderer まで。各surfaceの本格編集UXは後続。
  - 実Docker / 実SSH / 実remote daemon / 実外部CLI / 本物のSlack・Telegram・LINE・Email service credentialを使う長時間E2Eは環境依存の運用検証として残る。`GET /api/health.release.manual_gates` と `release.profiles[]` は、その未完了manual gateと本番運用profileを表示するための診断契約であり、Frontendから実runを起動しない。
  - Vitest / tsc はこの環境で無音ハングするケースがあり、ledger には代替検証と未完走ログを残している。
  - provider secret 入力、SecretRef raw value 表示、native session id 手入力、MCP process 直接制御、filesystem 正本の直接編集は作らない。

## 触らないもの

- UI 側で filesystem 正本を直接編集しない。
- UI 側で provider secret を保存しない。
- UI 側で ActionCatalog に risk / approval / policy を足さない。
- UI 側で `backend_waiting_for_native_input` を独自 approval として扱わない。
