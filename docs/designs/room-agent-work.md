## 1. 目的

Roomを開いて依頼すると、既定Agentが仕事を進める。必要に応じて専門Agentが参加し、人間は進捗を見て、止め、指示を変えられる。一人で使える体験を基本に、同じ仕事へ他の人が参加できるようにする。

Roomは継続する仕事と文脈の場所である。その中の個々の依頼を「仕事」として扱う。仕事のためにSessionを作成・選択する操作は利用者に要求しない。

中央の会話はAgentへの依頼・追加指示と結果を扱う。人間同士の相談は仕事に紐づくコメント欄で行い、「Agentに反映」を押した内容だけを追加指示として扱う。

## 2. 責務と基本単位

| 単位 | 責務 | 境界 |
| --- | --- | --- |
| Workspace | Agentプロフィール、Room、仕事の履歴、利用者が所有するKnowledgeとファイルを持つ | export / restoreと配置先変更の単位 |
| Room | 継続する文脈、参加者、権限、既定Agentを持つ | 仕事の閲覧・実行・共有の認可単位 |
| Agent | 名前、専門性、指示、利用するBackendの設定を持つ | Workspaceに登録する安定した主体。VMやモデルそのものではない |
| 仕事 | 一つの依頼、依頼者、追加指示、担当作業、結果、コメントをまとめる | Roomの下に置き、独立した権限階層を作らない |
| 担当作業 | 既定Agentまたは専門Agentへの割当、依存関係、実行状態を持つ | 一つの仕事の中の実行単位 |
| Backend Run | 特定のAgent・Backendによる一回の実行を表す | 再試行・担当変更では別の実行IDを使う |
| SessionRef | 外部エンジンの会話継続・復旧の参照を保持する | 内部専用。認可根拠や通常の画面階層にしない |

既定Agentは仕事の窓口・取りまとめを担当する。実際の開始許可、権限確認、キュー、停止、状態確定はSamuraiのCore / Runtimeが担当する。

## 3. AgentとRoomの関係

### 3.1 登録と既定Agent

- AgentはWorkspaceで作成し、名前・専門性・指示・Backendを設定する。人格と権限の正本を外部エンジンに移さない。
- Room作成時に、既存Agentを選ぶか、新規作成する。Roomには既定Agentを一つ設定する。
- Room、作成者のMembership、AgentのRoom権限、既定Agentの関連付けを一つの作成操作として確定する。途中失敗で利用不能なRoomや孤立したAgentを残さない。
- 既定Agentには少なくともRoomの閲覧・実行権限が必要である。編集権限は別に管理し、既定という理由で全権限を付けない。
- 同じAgentは、あるRoomの既定Agent、別のRoomの専門Agent、個人のDM相手になれる。実行の文脈と権限はRoomごとに分ける。
- Room Owner / Adminが既定Agentを変更できる。変更は新しい仕事に適用し、進行中の仕事の担当はそのまま記録する。進行中の担当変更は仕事の制御操作で行う。
- 既定Agentが無効化・権限取消・接続不能になっても、別Agentへ自動で差し替えない。履歴は開ける状態を保ち、実行できない理由と設定変更の導線を示す。

登録済みAgentの作成・編集・権限拡張は、人間の管理操作で行う。Agentの自動委譲は、既に許可された専門Agentへの仕事の割当に限る。

### 3.2 専門Agentの指定

- 通常の送信先は既定Agentであり、毎回のメンションを必要としない。
- `@Agent`または選択UIで、Roomで実行可能な専門Agentを指名できる。表示名の文字列だけで認可せず、選択したAgent IDを解決する。
- 明示指名した相手を担当として記録する。既定Agentが別の相手へ黙って置き換えることはしない。
- 複数Agentを指定した依頼は同じ仕事の担当作業として表示する。既定Agentが取りまとめるが、Runtimeが依存関係と書込み競合を確認して開始する。
- Agent同士の調整は仕事のActivity・担当一覧で追える。中央の会話へ全ての内部連絡を並べることを前提にしない。

## 4. 依頼・返信・コメント

| 操作 | 意味 | Agentへの影響 |
| --- | --- | --- |
| 通常の入力から送信 | Roomに新しい仕事を依頼する | 既定Agent、または明示指名した専門Agentで開始する |
| 「この仕事に返信」から送信 | 選んだ仕事への追加指示 | その仕事に指示の新しい版を追加する |
| 仕事のコメント欄に投稿 | 人間同士の相談・提案 | Agentを起動・継続・変更しない |
| 「Agentに反映」 | 選択したコメントを仕事の追加指示にする | 操作者の制御権限を確認して反映処理へ渡す |
| いいね | 人間の反応 | 実行指示・承認・自動学習の確定を意味しない |
| 添付 | 依頼またはコメントに資料を関連付ける | 添付先の用途・権限に従う |

返信中は対象の仕事と担当を入力欄に示し、解除すると新しい依頼へ戻る。完了した仕事への返信は、同じ仕事の追加作業として新しい実行を作る。過去の完了結果は履歴として残す。

コメントは依頼メッセージと種類を分けて保存する。未反映のコメントを、次の実行の指示、Agent向け会話履歴、自動学習による実行方針へ暗黙に混ぜない。

「Agentに反映」では、選択したコメントのID・版・本文のスナップショット、添付の参照、反映した人と時刻を保存する。送信前に対象の仕事と内容を確認できる。反映後にコメントが編集されても、既に渡した指示は書き換わらない。削除・権限変更で内容を確認できない場合は送信を拒否し、再選択を求める。

添付はアップロード成功とAgentによる参照成功を区別する。Serverが発行したファイル参照を使い、Clientから渡された任意のローカルパスをAgentへ直接渡さない。

## 5. 制御権限

全操作に現在のWorkspace MembershipとRoom権限を適用する。Organizationの役職だけではRoomの仕事を読んだり制御したりできない。

| 操作 | 必要条件 |
| --- | --- |
| 仕事・進捗・コメントの閲覧 | Roomのread権限 |
| 新しい仕事の依頼 | Roomのexecute権限 |
| コメント・いいね | Roomのedit権限 |
| 追加指示・コメント反映・担当変更 | 仕事の依頼者、またはRoom Owner / Adminであり、現在も必要なRoom実行権限を持つ |
| 仕事全体・担当作業の停止 | 現在のRoom参加者である依頼者、またはRoom Owner / Admin。停止のために新しい実行権限を与えない |
| Agent参加・権限・既定Agentの変更 | Roomの管理権限。Agentプロフィールの編集はWorkspace側の管理権限も確認する |

他のメンバーは、既存の仕事へコメントで提案できる。自分の依頼権限があれば別の仕事を開始できるが、他人の仕事の指示は上書きしない。

認証済みの操作者と、保存された依頼者・Room roleから制御可否を判定する。ClientやAgentが送った「依頼者ID」「管理者」という自己申告を信頼しない。委譲先にも元の依頼者を引き継ぎ、現在の人間の権限、AgentのRoom権限、仕事で許可された範囲の共通部分だけを使う。

依頼者またはAgentの権限が取り消されたら、新規開始・委譲・ツール操作を拒否し、進行中の実行を停止対象にする。停止結果の回収は内部の限定した処理として続ける。履歴の閲覧を回復させるために権限を自動追加しない。

## 6. 仕事のデータと処理

### 6.1 論理データ

以下は必要な関係であり、物理テーブル名を指定するものではない。PostgreSQLでID・関係・権限・履歴を保持し、ファイル本文は既存のconfigured storage rootに置く。

| 記録 | 必須の情報・制約 |
| --- | --- |
| Room設定 | 既定Agent ID、設定版、通常Room / Agent DMの種別。Agentは同じWorkspaceに存在する |
| 仕事 | Room、依頼者、窓口Agent、当初の依頼、現在の指示版、仕事の状態、制御状態、作成操作ID |
| 担当作業 | 仕事、親担当、担当Agent、依存関係、適用する指示版、実行の試行、結果参照 |
| 指示 | 対象の仕事・担当、本文、操作者、版、元コメントのスナップショット、受付・反映状態 |
| コメント・反応 | 仕事、投稿者、版、本文または反応、添付参照。実行指示と型を分ける |
| 実行の記録 | Backend Run、Agent設定の版、継続参照、権限の根拠、実行先、作業範囲、終端証拠 |
| 制御操作 | 停止・指示変更・担当変更の対象、操作者、操作ID、仕事の世代、受付と実行結果 |

同じ操作IDの再送は同じ結果を返す。同じ操作IDで本文や対象を変えた場合は競合として拒否する。指示の同時変更は期待する版と比較し、上書きを防ぐ。

### 6.2 処理の流れ

~~~mermaid
flowchart TD
  U[人間の依頼] --> A[認可と重複確認]
  A --> J[仕事と最初の担当作業を保存]
  J --> Q[実行キュー]
  Q --> D[既定Agentまたは指名Agent]
  D --> T[許可済み専門Agentへの委譲要求]
  T --> G[Runtimeが権限と依存関係を確認]
  G --> Q
  D --> E[結果とActivityを保存]
  E --> V[仕事の状態と結果を表示]
  C[人間のコメント] --> P[仕事のコメントを保存]
  P --> F[人間が選択してAgentに反映]
  F --> I[同じ仕事の追加指示を認可して保存]
  I --> Q
~~~

依頼・担当作業・起動予約・公開Eventの永続化を整合させる。実行の開始はDB確定後に行い、応答切断を理由に同じ外部操作を二度開始しない。通知が失われても、保存されたEventと起動予約から回収できるようにする。

担当作業の取得はleaseと世代番号で競合を防ぐ。lease切れだけで古い実行が止まったとは判断しない。古い実行の出力は証拠として残しても、新しい担当・指示の成果へ混ぜない。

仕事の完了は、必要な全担当の結果が揃い、起動中・待機中の担当、未反映の指示、未解決の承認や停止確認が残っていない状態で確定する。既定Agentの返答が終わっただけでは、仕事全体を完了にしない。部分的な失敗は残したまま示す。

委譲の受付は担当作業のIDを返し、子の完了までDBロックやHTTP接続を保持しない。親が結果を待つ場合は継続点を保存する。親が保持する書込み排他で子が開始できない場合は、親の実行を待機へ移し、実際に資源の使用が終わったことを確認してから排他を解放する。

子の結果は永続化し、依存条件を満たした親の継続を一度だけ予約する。親の外部Runが終了していても仕事は待機状態を保てる。仕事が停止中、指示が更新済み、または親が交代済みなら、古い完了通知から自動継続しない。

自動委譲には有限の同時実行数・委譲深度・総作業数・実行時間の上限を持たせる。値はRuntime設定として管理し、到達時は理由を表示して待機または停止する。再委譲による循環や、Agentの会話が無制限に新しい仕事を作る構造にしない。

### 6.3 並行作業と成果物

読み取りや、分離を保証できる作業範囲では並行実行する。同じ成果物や実行ディレクトリへ競合する書込みを行う場合は、先行作業の確定を待つ。

書込み範囲が不明な外部CLIは、実行ディレクトリ単位で保守的に排他する。ファイル名の自己申告だけで排他を解除しない。分離した作業ディレクトリからの反映も、参照した版を確認して競合を示す。自動で他人の変更を上書きしない。

Agentプロフィールの共用は、プロセス・実行ディレクトリ・資格情報の分離を意味しない。物理的な実行範囲は[Agent Backend設計](agent-backends.md)で扱う。

## 7. 停止・指示変更・復旧

### 7.1 停止

仕事全体の停止は、まずその仕事への新しい起動・委譲・自動継続の受付をDB上で閉じる。同じロック・世代確認を使うため、停止と同時に新しい子作業が開始される隙間を作らない。

次に未開始の担当作業を取り消し、既定Agentと全ての委譲先へ停止を要求する。担当作業だけの停止は、その担当と子孫を対象にし、別の仕事へ波及させない。依存していた作業は待機させ、勝手に代替担当を起動しない。

| 表示 | 根拠 |
| --- | --- |
| 停止要求中 | 操作を保存し、対象の実行へ停止を要求した |
| 停止済み | 対象の全実行の停止または未開始を確認し、新しい実行も開始されない |
| 停止を確認できない | 未対応、通信断、プロセス不明などにより一部の終端を確認できない |

全体停止の表示には、停止を確認できた数と未確認の担当を示す。既定Agentだけが止まっても仕事全体を停止済みにしない。停止前のファイル変更や外部送信は自動では元に戻らない。

### 7.2 指示変更と担当変更

指示変更は「受付済み」「反映待ち」「反映済み」「反映失敗」を区別する。仕事全体への変更は、影響を受ける未完了の担当作業を列挙し、担当ごとに適用した版を追跡する。

実行中に指示を渡せるBackendは、受付の証拠を取得する。渡せないBackendは、新規委譲を止め、影響する実行の停止を確認した後、新しい指示版で継続する。停止を確認できない間は重ねて起動せず、反映待ちの理由を表示する。

担当変更は旧担当の実行を確定させてから、新しい割当と実行IDを作る。旧担当の遅延応答を新担当の回答として表示しない。人間の停止が後から入った場合は、自動継続・担当変更を取り消す。

### 7.3 再接続と再起動

ClientはRoomと仕事を指定して履歴・現在状態を取得し、Event cursorから追いつく。状態の版を比較し、古い通知で新しい状態へ巻き戻さない。

Server再起動では、保存された停止要求を先に回収する。実行の所在・終端が確認できるものだけを再接続・継続し、結果不明の外部操作を無条件に再実行しない。仕事を「確認が必要」として残す場合も、対象・最後の証拠・選べる復旧操作を示す。

## 8. Agent DMと共有

Agent一覧の「会話する」から、本人とそのAgentのDMを開く。内部では専用の非公開Roomを使用し、通常のRoomと同じ認可・履歴・仕事の処理を通す。同じ本人・Agent・WorkspaceのDM作成は重複させない。

DMの既定Agentはその相手である。他の人が同じAgentを使っても、DMの履歴や外部Sessionを共用しない。通常のRoom一覧・会話・検索・Event・ファイルAPIでは、Workspace / Organizationの管理役職だけでDMの内容は閲覧できない。

この条件を共通のRoom認可に組み込む。DMではWorkspace Owner / AdminからのRoom role継承を使わず、現在有効な本人の明示的Membershipを必要とする。参加Agentは本人の依頼に基づく権限だけで実行する。人間を追加してDMを共有Roomへ変える操作や、管理者がDMの所有者を自分へ復旧する操作は認めない。本人のアクセス復旧は、同じAccountのWorkspace Membershipと本人との関連を再確認して監査に残す。

アプリ上のDM閲覧と、Workspace全体の管理用export / restore、配置先Serverの運用権限は別の境界である。既存の管理用BundleにDMの記録を含める場合は、その対象を明示する。DMを、Workspace全体のバックアップ権限やServer運用者に対する暗号化された秘密領域とは扱わない。

DMの成果を共有Roomへ渡す場合は、対象の結果・添付と共有先を選ぶ。選択した内容のコピーまたは明示的に共有したリソースを渡し、元DMの履歴・Membershipを自動で公開しない。共有先で新しい仕事を依頼する場合は、そこで再認可する。

仕事へ他の人が参加する際も、まずRoomへのアクセスを確認する。仕事のリンクを送るだけで閲覧権限は増えない。仕事だけの新しいACLは導入しない。

## 9. 保存・移植と検証

export / restoreにはRoomの既定Agent、Agent設定、仕事と担当の関係、依頼・コメント・反映履歴、Activity・ファイル参照を含める。IDを変える復元では全ての関連を対応付ける。

外部エンジンの資格情報、プロセス、端末依存の継続状態は可搬データと区別する。移転先で接続・権限を確認するまで実行を開始しない。実行中だった仕事は、履歴を保って復旧確認の対象にする。

検証する不変条件は、Roomをまたぐ漏えいがないこと、コメントだけでAgentが動かないこと、制御権限を偽装できないこと、停止後に新しい委譲が走らないこと、再送・再起動で外部操作が増えないことである。複数Account・実PostgreSQL・実Agent・Native Appによる確認条件は実装計画に定義する。

## 10. 対象外と未決定事項

クラウドVMの発行、Computer Useのライブ画面・操作引継ぎ、Agentの自動登録、全社横断のAgent市場、仕事単独のアクセス権はこの設計の対象外である。将来の実行画面は仕事・担当作業に紐づけられる接続点を残す。

製品の基本動作を止める未決定事項はない。ボタン文言、コメント欄の開き方、担当表示の密度は実機で利用者が評価して調整する。技術上の具体的な保存形式、Runtime上限値、Backendごとの能力確認は実装計画に沿って確定する。
