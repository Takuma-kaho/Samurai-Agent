## 1. 目的と責務

Samuraiが持つAgentの名前・専門性・権限・仕事を、交換可能なBackendで実行する。今回の完成対象はSamurai Native、Codex、Claude Codeとし、いずれも同じRoomの依頼・停止・継続・専門Agentへの委譲を扱えるようにする。

| 層 | 所有するもの |
| --- | --- |
| Workspace Core | Agent設定、Room認可、仕事・指示・履歴、承認の判断、公開Event |
| Runtime | 起動許可、担当作業、依存関係、実行範囲、制御、終端証拠の確定 |
| AgentBackend | Nativeまたは外部エンジンへの入力変換、起動・継続・停止、イベント正規化、能力の報告 |
| Samurai Native | 選択したproviderのAPI呼出し、文脈構築、Host / Runtimeによるツール実行への接続 |
| 外部エンジン | 自身の推論、計画、ツール実行、エンジン固有の会話状態 |
| Native App | 依頼と操作、現在状態・制約・証拠の表示 |

AgentBackendにRoomの認可判断や、複数担当を動かす製品ルールを持たせない。Samuraiは外部エンジンの推論ループを再実装しない。

## 2. 接続方式

技術選定として、既存の`AgentBackend`契約、`SamuraiNativeBackend`とprovider接続、Codex / Claude Codeの構造化CLIアダプターを拡張する。Phase 4の完成条件は、実エンジンで依頼・継続・停止・承認と復旧が成立することである。

NativeはGemini、OpenAI、Anthropicなど複数providerを選択し、各providerの公式APIをAPIキーで利用する。Codex / Claude Codeは利用者本人が各製品の公式ログインで認証し、サブスク利用を基本とする。APIキー認証にも対応する。サブスク資格情報は各製品の公式認証機構で扱い、Nativeへ流用しない。

ACPは、対応エンジンを同じBackend契約につなぐための追加アダプター候補とする。今回の必須プロトコルにはしない。単にACPへ置き換えても、人間の制御権限、仕事全体の停止、Room境界、実行先の分離はSamurai側に必要である。

| 接続 | 用途 | この設計での扱い |
| --- | --- | --- |
| Samurai Native + provider API | LLM呼出しとHost / Runtimeでの作業 | 既存Nativeを拡張する必須Backend。製品のprovider選択と検証用Gemini設定を分ける |
| Codex構造化CLI | 実行イベント、結果、エンジン固有の継続 | 既存アダプターを拡張する必須Backend |
| Claude Code構造化CLI | stream、結果、エンジン固有の継続 | 既存アダプターを拡張する必須Backend |
| MCP tool bridge | 認可済み文脈・ツール、Samurai管理下の委譲操作 | 実行ごとの限定された接続として利用する |
| ACP | 対応エンジンとの標準化された会話・制御 | 拡張点。導入時にも同じ能力・認可・終端の条件を満たす |
| A2A | 別システムのAgent間接続 | 今回の同一Workspace内の委譲には導入しない |

CLI引数とイベント形式は、実装時に実行するバージョンで確認する。存在確認だけを「接続済み」「継続可能」「停止確認済み」として報告しない。必須能力を満たせない場合はPhase 4の未完了事項として残し、代替接続を同じ契約内で検討する。

## 3. 共通契約と能力

入力はRoom、仕事、担当作業、Backend Run、Agent設定の版、認証由来の依頼者、指示版、許可された文脈・ツール・実行先を結び付ける。Clientから外部Session IDや任意の起動コマンドを指定させない。

| 能力 | 共通の意味 |
| --- | --- |
| 状態照会 | 未設定、設定済み、接続確認済み、認証が必要、利用不能と、その確認根拠を返す |
| 実行 | 同一Runの二重起動を防ぎ、構造化イベントと結果を返す |
| 継続 | 同じ認可範囲のエンジン会話を継続する。過去のRunは書き換えない |
| 停止 | 要求を受け付けたか、終端を確認できたかを別々に返す |
| 追加指示 | 実行中に配送できるか、停止後の継続が必要かを明示する |
| 承認・入力待ち | 何の操作に、誰の応答が必要かを構造化し、実行と応答を対応付ける |
| イベント | 順序、重複、関連Run、終端証拠を照合できる |

能力は`対応`と`実機で確認済み`を分ける。三つの必須Backendで利用可能な共通操作をUIに出し、方式の違いは必要な場面だけ説明する。

## 4. Sessionと文脈の分離

外部会話の関連付けには、少なくともWorkspace・Room・仕事・担当Agent・Backend・関連付けの世代を用いる。同じAgentが別RoomやDMで動いても、外部Sessionを共用しない。同じ関連付けに対する同時ターンも許可しない。

Roomの継続性はSamuraiが保存する依頼・結果・Knowledgeで支える。新しい仕事では、必要なRoomの文脈を限定して渡す。全ての仕事で一つの外部Sessionを使い回して並行実行を混線させない。

Samurai Nativeは外部Sessionのresumeを前提にせず、Samuraiの保存済み文脈から次のRunを組み立てる。停止ではAPI呼出しとHost / Runtimeのツール実行の終端を確認し、CLIを使わず同じ仕事の制御を成立させる。

- Agentの名前・役割・指示はSamuraiの正本フィールドから組み立て、実行時の版を記録する。
- 権限は文章の指示だけで実現せず、Coreの認可と実行先・ツールの制約で強制する。
- 未反映コメント、別Roomの履歴、他人のDM、権限外のKnowledgeは入力へ含めない。
- Backendを変更したら、そのBackendの新しい関連付けを作る。異なるエンジンのSession IDを流用しない。
- 外部Sessionが失効した場合は、Samuraiの記録から認可済み文脈を再構成できる。ただし実行結果が不明な操作を、そのまま再試行する理由にはしない。

## 5. 実行と委譲

以下は外部CLIの経路を示す。NativeではBackend内でprovider APIへ接続し、ツール実行と委譲をHost / Runtimeから同じ認可済み操作へ渡す。

~~~mermaid
sequenceDiagram
  participant C as Workspace Core
  participant R as Runtime
  participant B as AgentBackend
  participant E as 外部エンジン

  C->>C: 依頼と担当作業と起動予約を保存
  C->>R: 確定した実行を通知
  R->>R: 現在の権限と仕事の世代を確認
  R->>B: 認可済み入力で実行
  B->>E: 構造化入力
  E-->>B: 進捗と結果
  B-->>R: 正規化イベントと終端証拠
  R->>C: Runと仕事の状態を確定
  C-->>C: 公開Eventを保存して通知
~~~

外部エンジンから専門Agentへの依頼は、Samuraiのtool bridgeを通るDomain Operationで行う。認証された実行トークンから元の仕事・依頼者・呼出元Agentを解決し、対象Agentの現在のRoom権限と仕事の受付状態を確認する。

委譲は受付IDを返す非同期操作とし、子の結果と親の継続予約をRuntimeが保存する。親の実行終了と仕事の終了を分け、結果待ちからの再開では同じ仕事の新しいRunを使用できる。親の書込み排他が子を妨げる場合は、親を停止確認付きの待機へ移してから解放する。子の終了通知を受け取っただけで、停止済みの仕事を再開しない。

エンジン内蔵のsubagentは、Samuraiに登録した専門Agentと同一視しない。Samuraiの担当一覧へ載せる仕事は、Samuraiが割当・履歴・停止範囲を管理する。追跡できない内蔵の子プロセスを使用する場合は、親Backendが停止範囲と終端を説明できることを条件とする。

## 6. 実行先と承認

Backendプロセスは、認可された実行先で動かす。Native AppのあるPCで実行しているとは限らない。Hostedでは配置済みの実行先、Self-hostでは運用者が構成した実行先を使用し、今回新たにクラウドVMを発行する仕組みは作らない。

- 作業ディレクトリ、許可するツール、ファイルの受渡し先、エンジン認証の参照をRuntimeが解決する。
- Roomごとの認可と、プロセスのOS上のアクセス範囲を別々に確認する。ディレクトリを分けるだけでOS・ネットワーク・資格情報の隔離ができたとは扱わない。
- Backendが直接ファイル・シェルを使う場合は、その実行先とエンジンの制限設定で許可範囲を強制する。Roomをまたいで読める汎用ストレージやServerのsecretを渡さない。
- 制限を実現できない組合せは、制限付きAgentとして実行可能と報告しない。許可範囲を広げる自動fallbackも行わない。
- 資格情報の本文はrenderer、Agentプロフィール、チャット、公開Event、Workspace Bundleへ入れない。実行先の既存の安全な保存機構で管理する。

承認が必要な操作は、Samurai側の権限と既存のApproval Lifecycleへ結び付ける。Backendの待機要求にはRun・操作内容・応答ID・期限を対応付け、応答時にも現在の権限を確認する。期限切れ・停止後・旧Runへの応答は新しい実行へ転用しない。

プロンプトで「許可された」と言っただけでは承認にならない。承認要求を安全に橋渡しできないBackend操作は、拒否または利用不能として示す。全許可のCLI設定で帳尻を合わせない。

## 7. 停止と追加指示

### 7.1 停止の証拠

`cancelRun`の要求受付、プロセス終了、ツール・子実行の終了、仕事全体の停止は異なる状態である。Backendは担当する範囲の終端証拠を返し、Runtimeが仕事全体を集約する。

停止要求後は、プロセス終了やエンジンの確定イベントを期限付きで待つ。要求を送った直後の未確定状態を、最終的な停止成功にしない。期限を超えた場合は停止未確認として保持し、遅れて得た証拠を追記して再照合できるようにする。

CLIの親プロセスだけを終了させても、子ツールが残る場合がある。実行先が提供するプロセス群の制御・監視を使い、そのBackendが起動した範囲を確認する。既に外部サービスが受理した操作は取り消せるとは限らず、結果不明を隠さない。

### 7.2 指示の反映

実行中の追加入力に対応する場合は、配送先Runと指示版の受付を確認する。保存しただけの文字列を「反映済み」にしない。

Backendが実行中の入力に対応しない場合は、Runtimeが対象作業の新規委譲を止め、停止を確認し、同じ仕事の新しいRunを開始する。外部CLIはエンジンの継続機能、Nativeは保存済み文脈からの再構成を使う。外部会話を継続できなければ、確定した履歴から新しい外部会話を作ることを状態として示す。過去の副作用の再実行は行わない。

「反映済み」は、その版が次の実行または実行中の配送先に受理されたことを示す。Agentが依頼を達成したという意味ではない。仕事全体では各担当の反映状況を集約する。

## 8. Eventと復旧

正規化イベントには、Run、担当作業、Agent、指示版、順序、元イベントの識別子、発生時刻を対応付ける。不正なイベントは診断記録へ分け、別のRunへ補完して混ぜない。内部診断や機密を含み得る生出力を、そのまま公開Eventへ流さない。

プロセス起動・外部呼出しをDBトランザクション内で行わない。永続化した起動予約と一意な実行IDを使い、再起動後も開始済みかを照合する。外部サービスが冪等性を提供しない場合に、Samuraiの操作IDだけで完全な一回実行を保証したとは言わない。

| 障害 | 扱い |
| --- | --- |
| 未設定・認証切れ | 起動せず、設定または再認証へ案内する |
| 起動前の失敗 | 外部操作が未開始である証拠を残し、条件が整えば再試行する |
| stream切断 | 同じ実行へ再接続できるか確認し、切断だけを実行失敗・成功と決めない |
| プロセス終了・Server再起動 | Runと停止要求を照合し、確認済みの終端だけを確定する |
| 外部操作の結果不明 | 自動再実行を止め、確認に必要な証拠を表示する |
| Agentまたは依頼者の権限取消 | 新しい操作を拒否し、進行中の処理を停止対象にする |
| 移転先にBackendがない | 仕事と履歴を復元し、接続未設定として表示する |

## 9. 検証と拡張点

実装担当の実機検証はSamurai Nativeと、利用者が以前共有したGemini APIキーの無料枠に限定する。初回実行、仕事への追加入力、保存済み文脈からの継続、停止の要求と確定、承認待ち、失敗、再起動、Room / DM分離、Nativeを使う複数の専門Agentの実作業を確認する。他providerへの自動fallbackは検証設定で無効にする。

Codex / Claude Codeの実機検証は利用者が担当し、公式ログインによるサブスク利用とAPIキー利用、各制御、エンジン固有の継続、異なるBackendを使う専門Agentの共同作業を確認する。実装担当は実CLIを起動せずmock / fixtureで接続契約を確認する。利用者の結果が揃うまで外部連携は未検証とし、Nativeの成功で代替しない。

mockのイベント列は状態遷移を検証するために使い、実CLIの停止・継続の証拠にはしない。実行したエンジンのバージョン、設定条件、OS、実行先、DBとファイルの結果を記録する。

将来のComputer Useには、Runから実行先の識別子と表示可能な能力を参照する接続点を残す。ライブ画面・操作権の移譲・VM発行は別途設計する。現在のAgent登録とComputeの所有・権限を同じものとして保存しない。

製品方針に関する追加の未決定事項はない。Backendごとの承認・停止・継続の実証は、実装計画のPhase 4ゲートであり、文書作成時点では未検証である。
