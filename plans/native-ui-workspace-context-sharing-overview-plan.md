## 1. 何を実現するか

今の会話中心の画面を活かし、作業場所、過去情報、仕事の結果、設定への入口を分かりやすくする。同時に、Roomで得た知識とAgentを、自分で内容を確かめて他の人へ渡せるようにする。

今回の範囲は[要件定義書](../docs/requirements/native-ui-room-agent-sharing-requirements.md)と、[基本設計](../docs/designs/workspace-context.md)、[データ設計](../docs/designs/workspace-context-data.md)、[API・処理設計](../docs/designs/workspace-context-api.md)、[画面設計](../docs/designs/native-app.md)第11〜15章に従う。実装担当には、計画の要約だけで進めず、各工程で関係する設計の節を読むよう指示する。

| 対象 | 利用者から見た完成後の姿 |
| --- | --- |
| 作業場所 | 左上からWorkspaceを切り替え、Roomの親子関係を開閉して選べる |
| 検索 | 今いるWorkspaceで、自分が読めるRoom・会話・知識をまとめて探せる |
| 通知 | 完了・失敗・承認待ち・入力待ち・招待を確認し、対象へ戻れる。他Workspaceの未読にも気づける |
| Room上部 | 実際の参加者、既定Agent、Roomメニュー、左右の開閉操作を確認できる |
| 本人設定 | 左下の設定から全画面を開き、名前・回答設定・テーマ・接続を管理できる |
| Room・Agentの知識 | Roomは会話右側の設定、Agentは詳細画面から確認・編集できる |
| Room知識共有 | 選んだ知識を確認・編集し、限定または公開リンクで渡せる。相手は既存Roomへ取り込める |
| Agent共有 | 名前・人格・指示と、選んだSkill・知識を渡せる。相手は自分のWorkspaceに新しいAgentとして取り込める |

## 2. なぜこの順番で作るか

画面を先に完成させても、保存や権限の処理が揃っていなければ、押しても動かない、同じデータが二重に作られる、別Roomの情報が見えるといった問題が残る。まず共通の保存・権限処理を成立させ、各機能を接続してから、一連の実操作を確認する。

既存のRoom・Agent・知識・成果物の処理を使えるところから接続する。全体を作り直す計画ではない。

| 順序 | 工程 | 次へ進む基準 |
| --- | --- | --- |
| 1 | SI-00：設計と既存の接続先を確認 | 今回変える場所、維持するデータ、確認方法を対応付けられる |
| 2 | SI-01：共通の型・保存・権限を追加 | 後続機能が使う共通ルールと保存構造が揃う |
| 3 | SI-02：Agent知識・Room学習・旧メモリー廃止 | Roomや他の設定を守って廃止し、Agent知識を管理できる |
| 4 | SI-03：本人設定と実行への反映 | 本人の設定を別人と混同せず、次の依頼へ適用できる |
| 5 | SI-04：Workspace検索 | 読める情報だけを検索して取得できる |
| 6 | SI-05：通知 | 5種類の通知を保存し、既読・再接続・招待を扱える |
| 7 | SI-06：共有の発行側 | 確認した内容だけを発行・閲覧・停止できる |
| 8 | SI-07：取り込み側と保存・復元 | 新しい独立コピーをまとめて保存し、途中失敗から回復できる |
| 9 | SI-08：ナビ・ヘッダー・設定画面 | 実データを操作でき、元の入力・成果物へ戻れる |
| 10 | SI-09：検索・通知・共有の画面とリンク | BrowserとNative Appから一連の操作を行える |
| 11 | SI-10：受入確認と回帰確認 | 設計の確認条件に合格し、必要な未確認が残らない |

検索・通知・共有の発行側は基盤ができた後に独立して進められる。工程の区切りを作業終了にせず、実装依頼後は必要な修正・検証まで続ける。

## 3. 記憶と共有をどう扱うか

自動学習は、仕事をしたRoomの中で完結させる。同じAgentを別Roomで使っても、前のRoomで学んだ知識や会話がAgentの持ち物として自動で渡ることはない。Agentに持たせる専門知識は明示的に管理する。本人の指示は本人設定として扱う。

Workspaceはデータの所有・メンバー・保存・復元の単位として残す。廃止するのはWorkspace全体に適用する専用メモリーだけ。既存の専用メモリーは検証用データなので引き継がず、RoomやAgentへ自動移管しない。

共有は元データの共同編集や、元Roomへの招待ではない。発行前に選んで確認したコピーだけを渡す。受け手は内容と保存先を確認してから取り込み、その後は自分のデータとして編集できる。元と相手の変更は互いに反映されない。

限定共有では、指定した本人だけが読める。公開共有では、リンクを持つ人がログインせず読める。どちらも取り込みには本人認証と保存先の権限が必要。Room知識共有に会話履歴・Skill・設定を含めず、Agent共有に参加Roomの情報・元の認証・権限を含めない。

共有停止後は新しく読むことや取り込むことを拒否する。ただし、停止前に受付済みの同じ取り込み処理は再開できる。すでに読まれた内容や取り込み済みコピーは回収できない。この点は共有前と停止時に説明する。

## 4. 維持することと、防ぐ危険

今の3テーマ、会話・返信、DMの非公開境界、1体の既定Agent、成果物の編集・保存、Workspace切り替え、データの保存・復元を維持する。設定を開いても進行中の仕事を止めず、会話入力や未保存の編集を失わない。

| 防ぐ問題 | 確認すること |
| --- | --- |
| 他人・他Roomの情報が見える | 画面だけでなく共通処理とDBで拒否できる。検索の抜粋・通知・共有も確認する |
| 同じ取り込みが二重に作られる | 通信失敗後も同じ操作として結果を回収できる |
| 一部だけ保存され、使えてしまう | 本文準備と最終確定を分け、失敗した不完全なAgent・知識を公開しない |
| 確認していない内容が公開される | 保存済みの確認版だけを発行し、元データの更新を自動で混ぜない |
| 保存失敗や接続失敗を成功に見せる | 処理中・失敗・未確認・0件・完了を区別する |
| 廃止で他のデータまで消える | 専用メモリーだけを特定し、他の知識・Skill・設定・会話を保持する |
| 復元で古い共有リンクが復活する | 復元した共有は停止状態にし、再公開は新しい確認・発行から行う |

公開カタログ、Room全体の複製、共有コピーの常時同期・遠隔回収、新しいOrganization管理、外部メール通知、学習方式の作り直しは今回追加しない。

## 5. 何をもって完成とするか

要件定義書のA-01〜A-11と、4設計書のデータ・処理・画面の確認条件を、そのまま完成基準にする。設計書の要約や担当者の自己申告だけで完成にはしない。

実際のServer・PostgreSQL・本文保存先、BrowserとmacOS Native App、実Agentを使い、許可される操作と拒否される操作の両方を確認する。共有は発行者・正規受信者・対象外の人・未ログインで確認し、別Serverへの取り込みも通す。HostedとSelf-host、CIの確認結果は、それぞれ証拠を分ける。

3テーマ、通常幅・狭幅、キーボード、IME、設定から戻る、取り込み中に閉じて再表示する操作を確認する。既存の依頼、学習、DM、成果物、保存・復元が壊れていないことも影響範囲で確認する。

一連の検証を阻まない問題は記録し、先に検証を最後まで通してから、確認した必須問題をまとめて直す。修正後は関係する確認だけをやり直し、新しい根拠なしに問題探しを繰り返さない。情報漏えいやデータ破損に関わる問題は優先して該当処理を止め、原因を確認する。
